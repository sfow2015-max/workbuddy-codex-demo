# AI 软件项目协作与 GitHub 管理流程

**版本：V3.3｜修订日期：2026-10-22｜适用：ChatGPT、Codex、WorkBuddy 及其他 AI Agent**

**本版主题：项目开始前做可行性判断；关键依赖先实测；按能实际使用的业务闭环交付；批量测试优先本地脚本；Computer Use 默认不用、必要时短时受控调用；DPI 首次完整验收、后续按影响最小回归；延续条件自动合并。**

修订依据：V3.2 及用户补充的 DPI 验收效率要求。本版新增自适应 DPI 的首次完整验收与后续分级回归规则，避免每次无关改动都重复跑整套显示矩阵；保留批量脚本测试、Computer Use 最小化及既有数据安全规则。

本次是通用流程修订。文中的项目例子用于说明应如何验证，不代表已重新读取对应仓库、运行用户电脑、完成安装或解决现存问题。历史项目状态必须以执行时取得的新证据为准。

---

## 快速使用：以后按这套方式合作

1. **新项目先判断是否值得做、关键条件能否成立，再进入完整开发。** 有决定成败的未知依赖时，先完成最小验证。
2. **可行性分析分级。** 小范围修复和文案调整不重新立项；已有可靠证据可以复用。
3. **一次确定一个能用的业务目标。** 已授权范围内的调查、设计、开发、必要修复和验证连续完成，不把每个内部步骤都变成确认节点。
4. **第一批尽早提供最小操作入口。** 复杂视觉和周边功能可以后置，核心流程必须能实际操作。
5. **任务书与可发布源码优先进入 GitHub。** 用户只需要一段纯文本启动指令，不负责反复搬运文件。
6. **执行方完成本批开发、实测、自查、PR 和条件自动合并。** 合并条件统一见第五章，不再逐个询问是否合并。
7. **ChatGPT 根据实际提交和证据复核。** “报告说通过”“源码看起来正确”“本轮实际运行通过”分别表述。
8. **代码、构建包、已安装程序分别记录。** 每次交付明确用户现在能做什么、从哪里进入、使用哪一版。
9. **正式操作先检查已有授权。** 合并许可不自动包含正式部署和真实数据修改；已被明确授权的具体操作继续执行，不重复询问。
10. **关键假设不成立就换路线或给出停止结论。** 不以持续写界面、增加版本号或重复同一次失败代替进展。
11. **本批收尾后停止扩展范围。** 用户已明确授权多个阶段时，按约定关卡推进；未获授权的未来功能不能顺带开发。
12. **真实资料、凭据与模型文件按项目边界保留。** 私有仓库也不等于可以随意上传真实数据库、邮件或业务材料。
13. **优先用本地脚本、API、CLI、Playwright 或其他可控方式完成自动化。** Computer Use 不是默认路径；确实必须操作桌面界面时，只在必要操作期间调用，完成后立即结束，不长期占用或控制用户电脑。
14. **批量测试与 AI 判断分工明确。** 每档只切换一次设置，之后由本地脚本批量执行、自动汇总；AI 最后分析报告即可。工作流内部模型调用次数可以为 0，不得为了标榜 AI 参与而增加逐次调用。
15. **DPI 验收按风险分级。** 自适应 DPI 首次完成或发生核心机制变更时做一次集中验收并保存基线；后续仅按改动影响做最小必要回归，不为无关改动重复跑完整 DPI 矩阵。

默认顺序：

**需求目标 → 分级可行性判断 → 必要的关键能力实测 → 本批任务书 → 开发与业务验收 → 条件自动合并 → 合并后复核 → 按已有授权试用、安装或发布。**

具体任务的后续明确要求优先于通用模板；不能借模板忽略“只审查”“暂缓合并”等具体要求、未解决的阻塞或平台访问控制。

# 一、角色、依据与项目入口

## 1.1 协作职责

| 角色 | 主要职责 | 交付重点 |
| --- | --- | --- |
| 用户 | 确定要解决的问题、价值、取舍和真实使用反馈；决定新增业务范围与必要支出 | 方向与业务判断 |
| ChatGPT | 梳理需求、可行性判断、方案选择、任务书、源码与证据复核；按授权维护仓库文档 | 结论、依据、明确下一步 |
| Codex / WorkBuddy | 环境取证、验证实验、开发、运行、必要测试、构建交付、PR 和条件自动合并 | 可复核的实现与实测结果 |
| GitHub | 保存可发布源码、规则、任务、测试、脱敏报告、PR 与提交记录 | 版本与协作真源 |
| 正式运行环境 | 保存用户实际安装程序、业务资料、配置及必要备份 | 真实使用状态 |

ChatGPT 不与执行方同时争抢合并同一 PR。多 Agent 可并行处理独立模块或独立审阅；共享接口、文件归属和最终集成人要先明确，避免并发覆盖。

## 1.2 三类依据分开

- **需求依据：**用户已经明确的目标、约束和授权。
- **工程依据：**实际读取的仓库、分支、源码、依赖、提交及报告。
- **运行依据：**在指定机器、构建、权限和数据范围内真正执行过的操作。

GitHub 中的 `main` 是已合并基线，不天然等于已发布或已安装。文档写了“完成”，仍需对应实现和证据；报告中的实测属于执行方证据，复核者不能写成自己亲自运行。

## 1.3 每个项目只有一个当前状态入口

优先复用项目已有状态页；没有时可使用 `docs/PROJECT_STATUS.md`，不重复维护多套状态表。

| 字段 | 填写要求 |
| --- | --- |
| 用户目标与本批范围 | 本批要解决什么、怎样算可用 |
| 当前阶段 | 待验证 / 验证中 / 开发中 / 待复核 / 待试用 / 已完成 / 有阻塞 |
| 可行性结论与证据 | 引用报告或任务书，不只写“可行” |
| 当前任务、报告与 PR | 完整仓库根相对路径及相关链接 |
| 已合并代码与被测代码 | 分别指向真实提交；有差异时解释 |
| 可供试用的构建 | 应用版本、来源提交、产物位置；没有则写未生成 |
| 用户已安装版本 | 已核实的版本和核实日期；不知道就写尚未核实 |
| 当前阻塞及下一步 | 具体缺什么、由谁处理、什么结果可解除 |
| 执行状态 | 已发布任务 / 已实际启动 / 已完成 / 等待明确对象 |

状态页是导航，具体证据仍在任务、报告和 PR 中。不要为了在报告里写自身最终哈希而循环提交；最终 PR HEAD、merge SHA 可在合并后回读并由交付记录关联。

# 二、项目开始前的可行性分析

## 2.1 哪些情况需要做

| 工作类型 | 分析深度 | 进入开发前要求 |
| --- | --- | --- |
| 新项目、新运行平台、新外部数据来源或核心架构变化 | 完整分析 | 先验证会决定项目成败的关键依赖 |
| 已有项目新增重要模块、接入新模型或账号能力 | 针对新增部分分析 | 复用旧证据，验证新增权限、数据和业务链路 |
| 已验证路径上的小功能与局部修复 | 简短影响判断 | 说明影响、验收方法和必要回归即可 |
| 文案、普通样式和低影响文档修改 | 不单独立项 | 校对改动；不为凑流程编写整套测试 |
| 既有项目因同一根本问题反复阻塞 | 重审该关键假设 | 暂停依赖它的扩展开发，判断修复、换路或缩范围 |
| 只有资料、没有目标环境访问能力 | 先做资料判断 | 实测项标待验证，不宣布技术通过或失败 |

新项目可先交付“一页结论＋一张验证表”，必要细节放附录。分析深度由未知风险决定，不由项目名称或文档页数决定。

## 2.2 必须回答的八个问题

| 问题 | 需要得到的答案 |
| --- | --- |
| 1. 值不值得做？ | 当前痛点、使用频率、现有做法的代价，以及做完后可观察的改善 |
| 2. 有没有更省事的方案？ | 现有软件、已有项目扩展、开源复用和自行开发的适配程度与代价 |
| 3. 应该做成什么形态？ | 现有模块、独立桌面工具、网页或小程序；与设备、使用场景、数据边界的关系 |
| 4. 平台与权限是否成立？ | 当前账号、授权、运行与发布条件；哪些有官方依据，哪些需要实际测试 |
| 5. 数据能否取得且够完整？ | 来源、范围、字段、原件、历史、增量、附件、缺失检测及导出能力 |
| 6. 核心技术能否在实际环境运行？ | 目标硬件、软件版本、调用链、性能、稳定性和失败恢复 |
| 7. 日常用起来是否省事？ | 操作入口、录入步骤、弱网/切后台/误操作等适用场景，是否比当前方式方便 |
| 8. 长期维护是否值得？ | 开发工作量区间、估算前提、持续费用、存储增长、备份恢复、升级和退出成本 |

技术形态应围绕使用场景选择。与现有工作台共享用户、数据和操作流程的能力，可以优先评估模块化扩展；面向不同设备和场景的能力，要独立比较，不能因为已有工作台就全部塞进去。

工作量与费用必须区分一次性开发和持续运营。未知项写明估算前提；不能在权限、数据和核心链路尚未验证时给出确定的工期或承诺零维护。

## 2.3 开源项目调研如何影响决策

GitHub Star 数用于发现候选项目，还要核对：

- 解决的问题是否匹配；能复用的是完整应用、数据、组件，还是交互思路。
- 最近维护状况、发行版本、关键 issue、依赖和实际能否启动。
- 技术栈、运行平台、数据结构、登录方式与本项目的改造成本。
- 代码、动作资料、图片和其他素材各自的许可；没有明确授权依据时，不默认可复制或再分发。
- 是否能导出数据、删除依赖后是否还能使用，以及后续维护责任。
- 现有工程已能解决的部分是否值得替换；不为追求高 Star 无故重写。

涉及当前版本、平台规则、服务价格和许可条件时查原始来源，记录日期、链接以及所选仓库的版本或提交。其他人的演示不能代替目标账号和目标设备上的验证。

## 2.4 结论不能只写“建议开发”

| 结论 | 判定标准 | 下一步 |
| --- | --- | --- |
| 可进入开发 | 决定成败的关键条件已有足够实测证据，范围与成本边界明确 | 进入本批任务 |
| 有条件进入开发 | 核心链路已成立，剩余缺口不影响本批核心可用性 | 写明限制、负责人和补齐条件 |
| 待验证 | 核心条件缺证据，或目标环境暂不可用 | 只安排能消除未知的必要验证 |
| 调整路线 | 原路线不成立，但替代路线有望满足核心目标 | 比较代价；在已授权边界内验证替代路线 |
| 暂不实施 | 核心目标在现有权限、环境或成本边界内无法满足 | 说明原因、替代办法及重新评估触发条件 |

关键能力未验证不能归入“有条件可行”。也不能用总体评分掩盖致命依赖：用户要求包括联机存档，当前只证明了部分收件箱读取，就不能给“全量邮件方案可行”的结论。

如果必须降低用户原定目标，说明具体损失并取得相应范围决策；不能悄悄把“完整收录”改成“能看到一部分”。

# 三、关键能力的最小验证

## 3.1 验证方法

首轮优先处理最可能推翻方案的 1–3 个关键假设，其余未知列入记录。每项验证包含：

| 编号 | 关键假设 | 实验与环境 | 通过标准 | 证据位置 | 结果 | 失败后路线 |
| --- | --- | --- | --- | --- | --- | --- |
| F-01 | 具体能力与范围 | 实际账号/机器/版本、操作、数据范围 | 可观察且能复核的结果 | 脱敏记录、命令、提交或报告 | 通过 / 失败 / 待验证 | 替代方法及代价 |

验证顺序：

1. 明确目标和能够推翻方案的条件。
2. 读取适用规则、当前环境与已有证据，避免重复做已经证明的事。
3. 选最小且有区分力的样例；先写通过标准。
4. 用已授权的环境运行，记录返回结果、覆盖范围与限制。
5. 检查结果是否真的对应用户目标，区分“部分能力成立”和“全部能力成立”。
6. 得出第二章中的明确结论，并给出下一步最小动作。

允许为验证编写临时脚本、窄原型和必要界面。关键依赖未成立前，不投入依赖它的完整后台、大量页面和周边功能。可独立推进的部分继续完成。

## 3.2 实测与样本的边界

- 登录成功，只证明登录环节；模型列表、实际生成、隔离与业务调用分别验收。
- 读取若干邮件，只证明这些样本；全量覆盖还要验证枚举、分页、边界和数量核对方法。
- 本地模型能够加载，不代表目标业务耗时可接受。
- 开发工具预览成功，不代表目标手机、安装程序或发布环境已验收。
- 模拟后端成功，不代表真实服务成功；虚构数据可以用于真实应用和真实存储的实测。
- 测试中遇到权限限制，先说明限制和已验证范围；不能通过绕过访问控制“证明可行”。

调用、CLI、导出、浏览器或桌面自动操作都是待评估路径。先使用适合当前任务且已获授权的能力；工具不可用时如实交付可执行验证任务，不声称已在用户电脑后台运行。

## 3.3 投入边界与停止规则

验证任务应写明本轮投入上限或复盘节点、可尝试路线、费用边界和停止条件。默认不产生未经批准的新增实际支出。

以下情况需要停止当前路线的扩展开发并给出结论：

- 同一路径持续失败且没有新证据、新假设或可验证改法。
- 已确认存在不可绕过的权限、平台或目标环境限制。
- 继续投入超过已约定的时间或费用边界。
- 实测结果无法满足核心目标，继续开发周边功能也不能改变这一点。

不要机械规定“失败两次就问用户”。同一授权范围内、有新依据的可逆尝试可以继续；改变业务目标、增加未授权费用或突破数据边界时，再提出具体决策。

每轮结束必须交付：**已证实什么、尚未证实什么、是否值得继续、下一步做什么。**

# 四、从任务书到可使用的业务闭环

## 4.1 任务书最少包含

- 用户目标、当前问题和可行性结论及证据。
- 本批必须交付、不做内容、复用部分和关键依赖。
- 用户从哪个入口完成什么操作、会得到什么结果。
- 运行环境、数据范围、必要性能目标与异常行为。
- 验收标准、所需测试层级、构建包或运行交付方式。
- 允许触碰的账号、资料、费用与部署范围，以及已有授权。
- 关联仓库、基线、分支、文档路径、负责人、阻塞及停止条件。

按现有项目目录维护；新项目可选 `docs/feasibility/`、`docs/roadmap/`、`docs/acceptance/`。已有项目不为套模板移动目录或制造重复文档。

## 4.2 先有最小入口，再逐步完善

第一批正式功能交付应尽早形成：

**实际入口 → 必要输入或连接 → 核心操作 → 可观察结果 → 必要保存 → 再次打开确认。**

产品视觉精修可以后置，入口、状态与错误说明不能全部推迟。底层研究任务可以没有 UI，但应明确它是研究交付，不能宣称整个用户功能已完成。

每个可见功能回答：

| 用户问题 | 产品和交付应说明 |
| --- | --- |
| 去哪里用？ | 具体页面、按钮或命令 |
| 为什么现在不能用？ | 当前缺失的具体条件，避免只有灰色按钮 |
| 怎样变为可用？ | 用户可完成的恢复步骤，或明确指出须由执行方修复 |
| 怎么知道成功？ | 结果、保存状态和必要反馈 |
| 出错后怎么办？ | 可执行的重试、取消、恢复或查看原因入口 |
| 用的是哪一版？ | 程序中可核对版本；交付记录关联来源提交 |

安全限制保留，但要同时验证正确路径能够继续。不得为了让按钮变亮而取消本批隔离要求或让操作触碰错误数据。

## 4.3 执行前安全同步

确认 Git 根目录、远端、应用子目录、当前分支、HEAD 和工作区状态；读取适用 `AGENTS.md`、README、当前任务和上一批有关记录。

先 fetch 核对远端，再按可快进或已确认方式安全同步。不盲目 `git pull main`，不覆盖未提交修改，不默认 reset、clean、强推或混合不同工程历史。可以用隔离 worktree/分支处理独立任务，并明确基线。

一个业务目标内的必要步骤连续推进。无关重构、替换技术栈和未来功能留到后续；阻塞应说清事实和下一步，不用反复写全量架构报告替代执行。

## 4.4 按实际风险验证

| 改动类型 | 通常需要的验证 |
| --- | --- |
| 文档、文案、低影响样式 | 差异与内容检查；涉及布局时查看实际显示 |
| 普通业务功能或缺陷修复 | 必要构建、核心正向流程、针对性异常与受影响回归 |
| 外部服务或 AI 接入 | 目标环境真实请求、失败处理、权限与本批隔离要求 |
| 数据库、资金、状态或恢复逻辑 | 关键状态变化、不重复操作、失败无副作用及隔离恢复验证 |
| 桌面、手机 UI 与安装问题 | 对应设备/系统中的实际操作；不能只靠静态代码推断 |

不要求每次微小修改都运行全项目所有测试。测试范围由具体风险、任务书和仓库门槛决定；只为凑数量或复刻实现的测试没有价值。

## 4.5 自动化测试优先级与 Computer Use 使用边界

默认优先级如下，能用上一级稳定完成时，不升级到下一种方式：

1. 纯本地脚本、单元测试、命令行工具或直接调用本地服务。
2. 稳定的 API、CLI、Playwright / WebDriver 等可重复、可记录的自动化接口。
3. 必须验证真实桌面窗口、原生控件或只有 GUI 才能触发的行为时，才使用 Computer Use 或其他桌面控制工具。

**Computer Use 对用户电脑有干扰风险，默认不用。** 使用前先判断能否通过脚本、API、浏览器自动化或独立测试环境替代。确实必须使用时：

- 使用前先确认具体目的、目标窗口、最小操作步骤、预期时长和结束条件；能通过 API、CLI、脚本、Playwright 或独立测试环境完成时，不调用 Computer Use。
- 若操作可能抢占用户当前焦点、输入文本、切换窗口或影响正在进行的工作，优先改用独立测试环境/独立窗口；无法避免明显干扰时，先说明影响并取得用户明确同意。
- 只操作任务要求的目标窗口与控件；不在用户正在输入、会议、远程操作或其他敏感交互期间抢占焦点，不改变无关的全局设置。
- 操作完成、证据取得或遇到阻塞后立即结束调用，不保持后台会话，不把它作为持续轮询或批量回归的常驻执行器。
- 结束后检查并停止本次启动的自动化任务、临时窗口及不再需要的控制进程；不得关闭用户原本打开的应用或结束非本次启动的进程。无法确认清理完成时，必须如实报告。
- 优先使用独立测试账号、虚构数据和隔离环境；可能影响未保存工作时先停止并说明。
- 报告写明使用了何种执行方式、操作次数、运行环境与影响范围，不将脚本执行描述成 Computer Use。

若目标只是重复切换参数并跑兼容性矩阵，不使用 Computer Use 逐次操作。设置切换完成后，批量任务应交由本地脚本执行。

## 4.7 DPI 自适应与最小必要回归

**原则：不取消必要测试，而是不重复执行与本次改动无关的整套 DPI 矩阵。** 首次完成自适应 DPI 功能时集中验收并保存基线；后续按改动影响分级回归。

### DPI 测试分级

| 改动类型 | 必要验证 | 默认不需要 |
| --- | --- | --- |
| 文案、报告、纯文档或明确无关代码 | 差异检查、文档链接/格式检查 | DPI 测试、显示矩阵 |
| 与界面无关的业务逻辑 | 相关单元/集成测试，加一条必要核心流程（如用户入口受影响） | 全量 DPI 矩阵 |
| 控件定位、布局、窗口尺寸/状态、字体、缩放、自适应逻辑或坐标换算 | 受影响的代表性显示组合；覆盖变化的窗口/控件路径 | 未受影响的全部显示组合 |
| 首次实现自适应 DPI、重构 DPI/窗口协调核心、升级影响显示行为的 UI 框架/运行时，或出现跨屏/缩放回归 | 一次集中验收：支持范围内的主要缩放档、窗口状态及可用的混合 DPI/跨屏场景；保存基线 | 超出产品声明支持范围且没有现实使用需求的无限组合 |

### 自适应实现建议

- **优先语义控件定位。** 桌面自动化优先使用 UI Automation 的 AutomationId、控件类型、名称及控件模式；浏览器优先使用稳定 DOM 标识/角色定位。固定像素坐标作为最后选择。
- **DPI 变化后重新取证。** 感知 DPI/显示器变化，重新读取当前屏幕、窗口与控件位置，并清除旧坐标缓存；校验当前目标仍然正确后再继续。
- **统一坐标口径。** 自有桌面程序优先正确配置 PerMonitorV2 并处理 DPI/窗口变化；必须用坐标时，在公共适配层统一处理物理像素与逻辑坐标换算，不允许各模块自行重复换算。
- **不要用分辨率白名单代替自适应。** 以窗口/控件的实际几何、DPI 和工作区为依据；布局需考虑最小窗口、最大化/恢复、文字溢出和关键操作可达性。
- **不擅自更改用户系统设置。** 不为制造测试条件而自行切换 Windows 缩放、分辨率或显示器拓扑。优先使用脚本、独立环境、可注入几何或受控测试环境；模拟验证必须标注为模拟，不得写成真实跨屏实测。
- **明确外部软件边界。** 自适应执行器不能保证 Outlook 等第三方软件的所有界面、弹窗和动态布局都稳定。报告应注明实际验证的软件版本、环境、控件路径与未覆盖场景，不做无限兼容承诺。

### 首次验收与基线

首次完整验收按产品实际支持范围选择代表组合，可考虑 100%、125%、150%、200% 缩放，并在环境允许时覆盖跨屏/混合 DPI；不要求每个项目机械地测试所有档位。至少检查主窗口、关键弹窗/子窗口、缩放变化后的控件定位、文字溢出、关键按钮可达性、最大化/恢复及结束清理。

记录 Windows/运行时与应用版本、屏幕分辨率、缩放/DPI、显示器拓扑、窗口状态、测试方法（真实或模拟）、结果与截图/日志路径。后续回归引用该基线，只有被影响的组合变化时才扩大测试范围。

### 变更后的最小回归判断

1. 先检查本次差异是否触及 UI、窗口生命周期、DPI 感知、坐标转换、控件选择器或显示相关依赖。
2. 未触及上述路径：不重复 DPI 测试；运行本次改动的必要检查。
3. 触及部分显示路径：只跑受影响的代表性组合，并至少执行一条核心操作。
4. 改动自适应核心机制、显示框架/运行时或修复真实 DPI 回归：重新执行集中验收，更新基线。
5. 报告明确“未运行”的组合和理由，不把代表性抽样写成全覆盖。

## 4.6 批量兼容性测试与 AI 报告流程

对多档参数、浏览器设置、DPI 或类似兼容性矩阵，默认采用：**每档只切一次设置 → 本地脚本批跑 → 自动汇总 → AI 最后分析报告。** 工作流内部模型调用可以为 0。报告区分本地脚本批测、AI 逐次参与测试与真实桌面 Computer Use 测试；脚本批测不能称为“逐次 AI 混合测试”。原生 Computer Use 仅保留必要的代表性性能对照样本，单独报告，不纳入常规兼容性回归。

每个档位确认设置生效后，脚本连续执行用例并自动汇总通过/失败、耗时、错误分类、环境信息与结果路径；AI 在最后分析汇总与必要样本。设置状态无法确认时标记未知，不假设成功。

**批量测试执行细则：**

1. 开始前固定参数档位、用例矩阵、预期结果、超时与停止条件；测试过程中如需改口径，应标记为新批次。
2. 每个档位只切换一次设置。确认设置确实生效后记录配置值或证据；同一档位的重复用例全部由本地脚本批跑，不为每条用例重复切设置。
3. 每条用例至少保存档位、用例 ID、开始/结束时间或耗时、预期、实际结果、通过/失败/跳过、错误摘要及必要环境信息。优先输出 CSV/JSON 等机器可读记录，同时生成可读汇总。
4. 汇总需可追溯到单条用例，至少包括总数、通过数、失败数、跳过数、成功率、耗时统计，以及按档位和错误类型的分组结果；不能只报总成功率。
5. AI 只在批测结束后分析汇总与必要失败日志，不逐条参与执行。若未调用模型，报告明确写“工作流内部模型调用：0”。
6. 失败重试次数须预先设定并有限执行。保留首次失败与重试结果，不覆盖原始证据；达到停止条件后结束本批并汇总。
7. 原生 Computer Use 性能对照单独成组，只保留回答性能问题所必需的代表样本，独立记录环境、样本数、耗时口径与限制，不混入常规兼容性回归的通过率或覆盖率。

# 五、验收、条件自动合并与复核

## 5.1 最小验收记录

每批至少记录：

```text
Repository / PR / Branch:
BaseCommit:
TestedCodeCommit:
ReportCommit / PRHead:
ApplicationVersion / SchemaVersion（适用时）:
BuildArtifact / SourceCommit（交付包时）:
Environment / DataScope / MockedLayers:
TaskPath / ReportPath（仓库根相对路径）:
实际完成与用户入口:
通过 / 失败 / 未运行及原因:
已知限制与阻塞:
正式程序和真实数据是否发生变动:
```

测试代码提交之后只追加文档时，说明差异；出现代码变化则重新判断受影响测试。无需预先在报告中写入包含它自己的最终提交哈希。

至少区分三项：

| 维度 | 记录示例 |
| --- | --- |
| 运行层级 | 静态审查、单元、集成、真实应用窗口、目标设备、安装升级 |
| 数据及模拟范围 | 虚构数据、脱敏副本、经授权资料；哪些服务或故障被模拟 |
| 证据来源 | 本轮亲自执行、执行方报告、历史证据；各自的提交与日期 |

关键结论要有观察或断言。截图不能证明全部行为；大量测试通过不能代替缺失的关键路径。修复要证明问题被解决及正常流程可继续，不只证明更多操作被拒绝。

## 5.2 条件自动合并：唯一规范

延续用户已明确的持续授权：**本次任务覆盖的 PR，在条件全部满足后由指定执行方自动合并，不再逐个请求确认。**

条件：

1. 本批必须交付和关键验收已完成；有可核对的实测证据，关键测试未运行不能算通过。
2. 完整差异经过自查，无未解决阻塞、敏感资料、无关变更或越界行为。
3. 当前 PR HEAD 与被验证内容一致；仅文档追加要说明，实际组合发生相关代码变化要补充验证。
4. 合并前确认目标分支正确、PR 非草稿且无冲突、必需检查全部完成且通过、必需 review 和分支规则均已满足；失败或仍等待中的必要检查不得合并，不能用管理员绕过或关闭规则解决阻塞。
5. 明确合并的后续副作用。若合并会触发未授权的正式部署或真实数据动作，先处理该边界；已有具体授权的按授权执行。
6. 没有更具体的“只审查”“暂缓合并”或其他仍有效的限制。

没有 CI 就如实写没有配置，不能写“CI 通过”；本地证据不能冒充仓库要求的必需 review。涉及关键隔离、资金状态、正式写入或迁移的改动，应把相关代码与证据的独立复查纳入本批计划；这不等于增加逐 PR 用户审批。

优先使用支持预期 HEAD 的合并方式绑定被测提交；SHA 变化或发生冲突时重新核对，不盲目重试。遵守仓库合并方式，未另定时可沿用 merge commit。

合并后回读 PR merged 状态、merge SHA 与目标分支；目标分支已有后续提交时确认包含关系即可。返回排队或等待中就报告等待合并，不能写已完成。

## 5.3 合并与正式使用分别交代

- **生成验收包：**本批要求交付 Windows 包或其他构建时，完成构建、来源记录与交付，不因为“正式安装未授权”而卡住包的制作。
- **自动合并：**完成本批仓库收尾，不自动批准未来所有功能。
- **发布、覆盖安装、迁移真实数据：**核对是否已有具体授权。已有授权则执行并验收；缺少时先准备可审查的对象、备份与恢复方案，再一次性说明所需决策。
- **Tag：**按项目发布约定与授权处理，不给每个内部小批次随意打发布 Tag，不移动旧 Tag。

`AGENTS.md` 等旧模板不能成为重复索取已获授权的理由；也不能把本次通用文档修订当作对所有仓库、所有历史 PR 的即时操作授权。

## 5.4 ChatGPT 复核与修复

复核依据是确定的提交、任务书、差异、关键源码、测试与报告。结论分为通过、发现阻塞、证据不足、没有新成果。

- 未合并的问题：在原分支和 PR 追加修复。
- 已合并的问题：从最新已合并基线建立关联修复 PR，引用原问题，不改写历史。
- 影响核心使用或正式资料的问题：标明不宜进入相应正式使用环节；不自动强推回滚或用旧库覆盖新数据。
- 静态分析发现：写明“按代码路径可能发生，待复现”；没有现场证据不能写成已经造成损失。
- 修复记录：问题编号、被审提交、事实、故障场景、预期行为、最小修改和补测结果相互对应。

完成本批后停止扩展。下一批已有明确授权时，按约定关卡安排；否则给出建议，不擅自启动。

# 六、“拉取”、交付回报与工具阻塞

## 6.1 用户说“拉取”时

1. 定位目标仓库和项目当前状态入口。
2. 检查 `main`、相关最近合并 PR、相关未合并 PR 与分支。
3. 固定本次审查提交，对比上次已审基线；同时检查报告和评论中的新证据。
4. 只复核新增或受影响部分，必要时追溯相关实现。
5. 明确当前结论、可用状态、阻塞和最小下一步。

`open PR` 为空不等于没有成果；`main` 未变也不等于 PR 分支没有更新。仅任务书改变不算修复完成，评论声称完成也要核对对应代码。

远端没有变化时，报告最后观察到的提交和时间；不能据此猜测本地究竟未完成还是未推送，也不对同一提交反复宣称“本轮新修复通过”。

读取远端文件不是更新用户电脑。只有实际执行并验证本机同步后才能说已完成本机拉取。

## 6.2 日常回报先回答用户关心的问题

推荐简短格式：

```text
结论：已完成 / 有阻塞 / 待验证 / 没有新远端成果。
现在能用：具体能力及入口；不可用时写明原因。
交付状态：代码是否合并、是否有试用包、用户安装版本是否已核实。
验证情况：关键实测结果及尚未覆盖部分。
下一步：具体动作、负责人、是否已实际启动。
追踪：任务 / PR / 被测提交 / 合并提交 / 报告位置。
```

用户无需先理解一串 SHA 才知道能否使用。技术坐标仍需保留在可核对记录中。

## 6.3 工具连接失败先取证

优先调用实际可用的连接器、API 或 CLI。读取私有 GitHub 不用公开网页搜索替代。

| 实际观察 | 正确处理 |
| --- | --- |
| 元数据能读，单文件 404 | 核对 ref、真实目录、大小写、是否推送，不宣布整个连接不可用 |
| 搜索无结果，已知路径可读 | 按确定 ref 和路径直接读，不等搜索索引 |
| 授权或访问错误 | 报告具体动作与结果，核对当前能力和授权范围 |
| 工具未提供某项操作 | 明确缺哪项能力，使用允许的替代方式或给执行方短指令 |
| 新聊天中成功 | 只证明该次成功，不据此编造旧故障根因 |

确有工具阻塞或用户要求文件交付时，可以交付 Markdown；应写清是否已经同步远端。没有真实启动入口，就不要声称 Codex 或 WorkBuddy 已在后台执行。

# 七、源码、真实资料与正式升级

## 7.1 仓库至少要有可审查的源码

长期开发基线应包含可发布源码、构建与必要测试脚本、虚构夹具、README、适用 `AGENTS.md`、任务和脱敏验收记录。只有 docs 和 README，不能声称完成代码级审查。

本地与远端差异先核对。正式工程与脱敏副本是不同历史时，只移植可发布变更并记录对应关系；不能直接混合历史，也不能用脱敏初始化资料覆盖正式工程。

## 7.2 四套坐标继续保留

| 对象 | 核对内容 |
| --- | --- |
| 远端待审代码 | 仓库、分支、PR、HEAD |
| 实际测试环境 | 被测提交、应用和数据结构版本、硬件、权限、数据性质 |
| 已合并或已发布版本 | merge SHA、Tag、构建产物来源 |
| 用户正式环境 | 实际安装版本、正式基线、资料位置、结构版本及升级时间 |

公共或脱敏记录使用角色名和基线标识；敏感完整路径、账户信息等留在已授权的本地范围。

## 7.3 提交前检查真实内容

不要把 `git add .` 作为默认收尾。只暂存本批相关文件，检查 staged diff 与将引入远端的完整差异。

按项目排除：真实数据库及备份、邮件原件与附件、凭据、个人配置、原始业务日志、含真实资料的截图、大模型、未经确认的安装产物和构建依赖。可提交代码生成的虚构夹具、公共配置模板及脱敏证据。

`.gitignore` 不能清除已被跟踪的文件或历史泄露。发现敏感资料已进入历史时，停止继续传播并说明情况，按具体授权处理凭据和历史清理；不擅自强推。不得让用户在聊天里粘贴密码或令牌。

## 7.4 数据恢复和升级要能验证

涉及正式数据操作，先核对具体对象和已有授权。需要备份时采用项目已验证的一致性方法，并在隔离路径验证恢复、记录、结构和业务可用性；只看到备份文件不够。

代码回退与数据恢复分别设计。旧备份只能恢复旧时点，不能为了回退程序而覆盖新版已经产生的新记录。不要只移动仍在使用的数据库主文件。

交付安装应从已审核基线构建，核对正式工程差异，防止混入测试种子、示例账户或另一套数据目录。原文已授权的只读查询，也要保留其只读边界。

# 八、结合当前项目的验证重点

**以下是验证清单和适用示例，不是对各项目最新状态的验收结论。**

## 8.1 凯胜工作台：邮件原件与每日摘要

先证明数据入口和保存质量，再展开阅读器、搜索和摘要。

| 项目目标 | 验证重点 |
| --- | --- |
| 全部邮件，含联机存档 | 识别实际邮箱环境；分别检查收件箱、已发送、其他文件夹、联机存档；验证分页、时间边界、数量核对和缺失提示 |
| 查看原件 | 先定义原件：正文、HTML、头信息、附件、内嵌图片以及能否取得可重新打开的原始文件；逐项报告能保存什么 |
| 保留现有成果 | 原有摘要、附件归档、处理状态和记录关联不能被新收录流程覆盖或丢失 |
| 每日摘要 | 摘要关联到具体来源；摘要生成失败不影响原件阅读；收录不完整时明确摘要覆盖范围 |
| 长期收录 | 增量更新、断点恢复、重复导入去重、同名附件和错误可追踪 |
| 只读边界 | 查询、打开、导出等操作是否会改变原邮箱的已读等状态须验证；不发送、不删除、不移动原邮件 |

“看到网页中一页内容”“取得搜索结果”“复制到正文”分别说明证据范围。浏览器自动化或桌面操作都只是候选路径。优先评估 API、导出能力和脚本化浏览器自动化；仅当必须验证原生桌面行为时，短时调用 Computer Use，操作后立即结束。不能仅凭能打开 Outlook 就承诺全量稳定收录。

推荐先评估当前可用的正式接口或导出能力，再按已授权条件验证浏览器、桌面路径。某路线失败不等于目标必然不可实现；如果各路线都不能满足完整性，给出清楚的范围缺口和替代方案。

原件保真度与 Outlook 界面逐像素复刻分开验收。必须明确用户需要保存的内容与可接受显示差异，不能用摘要代替原件。

## 8.2 凯胜工作台：AI 接入

分别记录：登录、模型信息、额度信息、实际生成、本批隔离要求、业务结果、异常处理。

个人技能、配置、文件访问、工具执行、网络权限及凭据等隔离边界按实际接入机制与任务书逐项验证；仅凭换了工作目录或界面显示已连接，不能宣称隔离完成。

用户已经要求隔离成立后才能调用时，先验证隔离，再在许可条件下发起最小业务请求。未满足隔离不要为了“跑通一次”先发送真实业务数据。

接入界面应展示当前可验证的状态、正在执行的业务、阶段、已耗时、最近结果和失败原因。进度只能展示有依据的阶段或数量；无法测得剩余量时不编造百分比和完成时间。

## 8.3 Local AI Launcher：目标硬件、模型与 DPI

以实际机器、实际模型文件、量化、上下文及运行配置为准，验证加载、首个输出等待、持续输出、峰值资源占用、停止、失败恢复和业务体验。用户的 RTX 5060 8GB 与 CPU/GPU 混合运行需求不能仅靠模型名称判断。

工作台和启动器的职责应明确：哪个负责启动与停止服务、哪个发请求、哪个显示状态；先验证现有接口能否满足，再决定是否同时修改两个项目。

DPI 采用“首次集中验收并保存基线，后续按影响最小回归”。首次实现或修改自适应核心机制时，按实际支持范围验证代表性缩放、窗口状态及可用的混合 DPI/跨屏场景；100%、125%、150%、200% 是候选档位，不是每次都要重跑的固定清单。纯文案和无关逻辑不跑 DPI 测试；业务逻辑只测相关逻辑与必要核心流程；控件定位、布局、坐标换算或 DPI 机制变更只测受影响组合。没有真实运行的环境必须标为未验证；模拟几何测试不能声称真实跨屏已通过。

## 8.4 健身微信小程序

首个闭环建议：建立器械 → 定义调节项 → 关联动作和训练部位 → 记录一组 → 保存 → 下次恢复上次设置并查看历史。

- 器械与训练动作分别建模：同一器械可关联多个动作，同一动作可用不同器械完成。
- 座椅、靠背、滑轮高度、握把等作为用户可自定义的调节项，不依赖预置所有型号。
- “当前常用设置”和“某次训练实际设置”分别保存，修改常用值不能改写历史。
- 在实际手机上检查输入步骤、切后台、弱网、重复提交和再次打开；数据导出/备份与恢复要有方案。
- 账号、调试、长期使用及发布条件以当前官方规则和实际账号核对；预览成功不等于正式使用条件已满足。
- 开源项目按第二章筛选；训练记录、器械设置和素材可以分别评估复用，不默认高 Star 的原生 App 能直接变成微信小程序。

该项目与工作台的桌面办公场景不同，应单独判断手机端形态和日常操作负担。

# 十、在各仓库采用本流程

本文件是跨项目规范，不是任何项目的全量功能需求。具体仓库只需保留短规则和实际任务入口，避免复制多套互相矛盾的长模板。

建议 `AGENTS.md` 中保留以下执行要点，并引用仓库中实际存在的流程文件：

```md
# Agent Development Rules

1. 开始前确认仓库、分支、HEAD、工作区和适用规则，安全同步，保留用户修改。
2. 新项目或新关键依赖先做分级可行性判断；核心未知先验证，小改不重复立项。
3. 读取当前任务、可行性证据和关联验收；一次完成已授权业务目标的必要步骤。
4. 实际入口、核心操作、可观察结果和必要保存构成正式功能的最小交付。
5. 按任务风险做实测和回归，区分本人运行、他人报告、历史证据与模拟范围。
6. 仅提交本批可发布源码和脱敏证据，不上传真实资料、凭据、模型或无关产物。
7. 本批满足通用流程的全部合并条件后允许自动合并并回读，不逐 PR 重复询问。
8. 不绕过保护、必要 review、权限或未解决阻塞；具体暂缓要求优先。
9. 修复未合并 PR 沿原分支；已合并新建关联修复 PR，不强推或改写历史。
10. 构建、发布、覆盖安装和真实数据操作分别判断，已有具体授权不重复索取。
11. 更新统一状态入口，报告能用什么、交付/安装状态、证据和下一步。
12. 完成本批后停止扩展；没有实际启动、合并、安装或运行，不声称已经完成。
```

对旧流程的同步应限定在用户授权维护的仓库。先读取项目更具体的规则，保留业务、数据和发布限制；本轮文档更新不自动批量改动其他项目。

## 附录 A：资金与状态类项目的专项规则

本附录继承 V2.1 中财富工作台的经验；只在适用项目执行，不要求普通启动器增加金融模块。

1. **交易、估值和人工对账调整分开。** 保留来源、目标、原币金额、费用和业务含义。余额增加不能直接等同投资收益，不能用现值推造历史成本。
2. **期初接管不重复扣款。** 保留未知成本、份额和净值，明确产品与账户归属；前端筛选和后端校验都要符合规则。
3. **同币种无费内部转账总额守恒。** 两端联动、失败整笔回滚。跨币种保存实际收付与估值口径，不把不同币种原始数字直接相加。
4. **费用和估值差可解释。** 例如实收美元 U、人民币价款 C、费用 F、估值汇率 v，未舍入估值变化为 `U × v − C − F`；它是对账关系，不是收益预测。
5. **待确认、取消受理和到账分开。** 已付款资金只计一次，确认不再扣款，取消受理不提前恢复现金，实际退款到账才恢复。预计日期不自动触发确认、到账或计息。
6. **请求重试与并发不重复记账。** 检查同 ID 重试、同 ID 不同内容、不同 ID 竞争终态、提交成功后响应丢失，以及锁定、刷新、重开和切库。
7. **恢复以后仍能合法继续。** 旧备份缺少请求不证明原操作未入账；读取失败也不代表未入账。区分当前库、独立其他库及同一资料恢复到新路径，不靠删除恢复标记或永久禁用绕过核对。
8. **未支持的业务明确说明。** 部分处理、费用和赎回等按范围验收，不用人工补差额掩盖未实现能力。
9. **测试覆盖结果和无副作用。** 错误账户组合拒绝且无入账；正确组合可完成后续业务。数据库原子提交、不可变事件、状态关联、版本检查与前端反馈应相互对应。
